# Specialized Project

This repository extends the supplementary material of **SAC4BN**:

> **SAT-based Method for Counting All Singleton Attractors in Boolean Networks**  
> Rei Higuchi, Takehide Soh, Daniel Le Berre, Morgan Magnin,  
> Mutsunori Banbara, Naoyuki Tamura  
> *IJCAI 2025 (in print)*

It integrates an additional **PFVS-based method** and provides a  
**fully reproducible experimental pipeline** for:

- **fASP-c** (conjunctive encoding)
- **fASP-s** (source encoding)
- **H.E.** (Hybrid Enumeration / BMSA)
- **PFVS** (Positive Feedback Vertex Set)
- Unified log analysis, tables, and cactus plots

---

## What's new

- **ADF benchmark.** The 276 ICCMA 2019 ADF instances used by BAss
  (Pastva & Trinh, 2026) are translated into `.bnet` Boolean networks whose
  fixed points are the 2-valued models of the ADFs
  ([ADF Benchmark](#adf-benchmark-iccma-2019)).
- **Local rerun of all solvers.** `run_benchmarks.py` reruns fASP-c, fASP-s,
  H.E. and PFVS on every benchmark set on your own machine, with the protocol
  of the original runs, and writes logs that the analysis scripts read
  ([Rerunning the Solvers](#rerunning-the-solvers)).
- **PFVS converter fix.** `PFVS/converter_pfvs.py` renamed variables one at a
  time, so a network whose variables are already called `x<N>` (all Random
  instances) could be turned into a different network (e.g. `x3 -> x2 -> x5`).
  It now renames in a single pass, which is also much faster on large files.
  BBM and Selected conversions are unchanged.
- **Analysis scripts.** They can now read the rerun logs (`LOGS_DIR`), report
  runs that have not been done yet as `NOT_RUN` instead of crashing, detect
  out-of-memory relative to the memory limit of each run, and keep PFVS's own
  outcome (`REFUSED` when its feedback vertex set exceeds 30) instead of
  reporting every PFVS failure as `TIMEOUT`
  ([Log Analysis](#log-analysis-and-result-generation)).

The logs in `logs/` are those of the original SAC4BN runs (their `# Host:` and
`# Start date:` headers show where and when they were produced). Reruns go to
`logs_rerun/`, so both can be compared.

## Rerunning the Solvers

`run_benchmarks.py` runs the solvers on the benchmark sets with the protocol
of the original runs:

- each solver runs in its Docker image under GNU time (`time -v`);
- CPU time is limited to 1800 s (30 min) per process, like `ulimit -t`, and
  memory with no swap;
- fASP-c / fASP-s run `fASP FILE -c -m 0 [-e source]`, H.E. runs
  `/app/solve-bmsa.sh HEAP 1g h3 FILE` (on the biodivine SBML files for BBM,
  as originally), and PFVS runs `java -jar FPCollector.jar FILE.bn -m`.

Every log records the machine (CPU, RAM, OS), the date and the limits.

Requirements: Linux or WSL 2 (Ubuntu), Docker (on Windows: Docker Desktop with
WSL integration enabled), Python 3, and the two images above.

Quick test (about a minute):
```sh
python3 run_benchmarks.py --tools fasp_c fasp_s he --sets selected --limit 2
```
fASP-c, fASP-s and H.E. on BBM, Selected and Random:
```sh
python3 run_benchmarks.py --tools fasp_c fasp_s he
```
All four solvers, including PFVS:
```sh
python3 run_benchmarks.py
```

| Option | Meaning |
| --- | --- |
| `--sets bbm selected random adf` | benchmark sets (default: `bbm selected random`) |
| `--tools fasp_c fasp_s he pfvs` | solvers (default: all) |
| `--time-limit 1800` | CPU seconds per process |
| `--memory 12g` | memory per run (default: 80% of Docker's memory) |
| `--heap 10g` | Java heap of H.E. and PFVS (default: memory minus 2 GB) |
| `-j 2` | runs in parallel (default 1; timings are less comparable with more) |
| `--only 'model_00*'`, `--limit 5` | run a subset |
| `--logs DIR` | log directory (default `logs_rerun/`) |
| `--force` | redo runs that already have a log |
| `--dry-run` | print the Docker commands only |

Notes:

- **Resuming.** Finished runs are never repeated: after Ctrl-C (or a crash,
  or a reboot), run the same command again to continue.
- **Duration.** Most Random instances run until the 30-minute limit, so the
  Random set alone takes days. Running `--sets bbm selected` first gives the
  main results sooner.
- **Memory on Windows.** WSL gives Docker half of the RAM by default. To give
  it more, create `C:\Users\<you>\.wslconfig` containing `[wsl2]` and
  `memory=14GB`, then run `wsl --shutdown` and restart Docker Desktop.
- **WSL.** Run from the Linux file system (e.g. `~/Specialized-Project`)
  rather than `/mnt/c/...`: it is much faster, and a folder that is changed
  from Windows cannot break a long run.
- **Outputs.** Logs go to `logs_rerun/` in the same layout as `logs/`. PFVS
  result tables are written to `logs_rerun/pfvs/pfvs_<set>_results.csv`.


## Running the PFVS Tool
`python3 run_benchmarks.py --tools pfvs` does the steps below for every set,
measures CPU time like the other solvers, and records whether PFVS solved,
timed out, ran out of memory, or refused the instance.

Step 1: Convert .bnet to .bn
PFVS requires .bn input files.

```sh
cd PFVS
python3 converter_pfvs.py Examples/BBM
python3 converter_pfvs.py Examples/Random
python3 converter_pfvs.py Examples/Selected
```
Step 2: Run PFVS
```sh
python3 run_pfvs_bbm.py
python3 run_pfvs_random.py
python3 run_pfvs_selected.py
```
This generates:

pfvs_bbm_results.csv

pfvs_random_results.csv

pfvs_selected_results.csv

Move them into the analysis folder:

```sh
mv pfvs_*_results.csv ../logs_analysis/results/
```

Notes on these scripts:

- FPCollector does not attempt networks whose positive feedback vertex set has
  more than 30 nodes: it prints `Size of P set = N. No fixed points will be
  calculated.` and exits at once. The `run_pfvs_*.py` scripts record such
  instances as `timeout`.
- They read `examples/<set>` (lower case), which only matches the
  `Examples/` folder on case-insensitive file systems (Windows, macOS).
- They measure wall-clock time, while the other solvers are compared on CPU
  time.

## Log Analysis and Result Generation
All commands below are executed from logs_analysis/.

```sh
cd logs_analysis
```

Choose the logs to analyse:

```sh
export LOGS_DIR=../logs_rerun     # logs written by run_benchmarks.py
cp ../logs_rerun/pfvs/pfvs_*_results.csv results/
```

or, for the original logs, which are stored as `.log.7z` archives, extract
them first (e.g. with `7z`) and keep `LOGS_DIR` unset (it defaults to `../logs`):

```sh
find ../logs -name '*.log.7z' -execdir 7z x -y {} \;
```

Step 1: Generate Base Result CSVs
```sh
python3 fps_and_cpu.py
python3 num_solved.py
```
Step 2: Merge PFVS Results
```sh
python3 merge_pfvs_into_results.py
```
Step 3: Regenerate .dat Files
```sh
python3 regen_dat.py
```
Step 4: Regenerate Solved-Instance Tables
```sh
python3 regen_solved_csv.py
```
Step 5: Merge .dat Files for Cactus Plots
```sh
cat results/time_for_cactus.dat results/time_fasp_for_cactus.dat \
  > results/time_all_for_cactus.dat
```

In the CPU-time tables a solved run shows its CPU time in seconds; otherwise:

| Label | Meaning |
| --- | --- |
| `TIMEOUT` | CPU time limit reached |
| `OUT_OF_MEMORY` | killed above 75% of the run's memory limit (60 GB for the original logs), or Java `OutOfMemoryError` |
| `ERROR` | any other failure |
| `REFUSED` | PFVS only: positive feedback vertex set larger than 30 |
| `NOT_RUN` | no log for this run yet |

## ADF Benchmark (ICCMA 2019)

The 276 ICCMA 2019 ADF instances used by BAss (in
`benchmarks/ADF/ICCMA2019/adf/`) are translated into `.bnet` networks whose
fixed points are the 2-valued models of the ADFs:

```sh
python3 ADF/adf_to_bnet.py
```

The networks are written to `benchmarks/ADF/ICCMA2019/bnet/` (about 1.5
minutes; 204 instances are translated directly and 72 use auxiliary variables
because their XOR formulas would otherwise grow exponentially). See
[ADF/README.md](ADF/README.md) for the translation.

The solvers run on them like on the other sets:

```sh
python3 run_benchmarks.py --sets adf --tools fasp_c fasp_s he
```

The logs go to `logs_rerun/<solver>/adf/`. The analysis scripts in
`logs_analysis/` do not include the ADF set yet.
